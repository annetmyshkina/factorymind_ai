Документ описывает назначение системы, границы, доменную модель, архитектуру,

есть база, но этап не закрыт; **план** — запланировано.

## 1. Назначение

FactoryMind AI — backend-платформа для мониторинга промышленного оборудования,
управления инцидентами и **воспроизводимого сравнения ответов языковых моделей**
на производственных сценариях.

Две равноправные части:

1. **Производственная система** — оборудование, телеметрия, правила мониторинга,
   отклонения, инциденты с историей устранения.
2. **AI-платформа** — единый шлюз к моделям, сохранение вызовов и метаданных,
   эксперименты по сравнению моделей, оценка качества ответов.

Связка частей — принципиальная: модели решают реальные задачи внутри домена
(объяснить инцидент, предложить действия), но **не принимают решений за backend**.

### 1.1. Цели

- Надёжно принимать телеметрию по HTTP и MQTT, фиксировать отклонения.
- Вести инциденты с конечным автоматом статусов и полным аудитом.
- Дать единый интерфейс к LLM, не зависящий от вендора и модели.
- Сохранять всё, что нужно для воспроизводимости: провайдер, модель, версию
  промпта, параметры генерации, время, токены, стоимость.
- Сравнивать модели по независимым критериям, а не по одному «общему баллу».
- Разделять объективные проверки (код) и субъективные оценки (LLM-as-a-Judge).

### 1.2. Не-цели (текущий горизонт)

- UI и личный кабинет.
- Автоматическое закрытие инцидентов моделью.
- Управление производственными заказами и расчётом расписания (возможно позже,
  с детерминированным планировщиком).
- Аутентификация и разграничение ролей (см. открытые вопросы).

## 3. Ограничения и допущения

1. **Провайдеры без VPN.** Используются локальная Ollama и Chat
   Completions-совместимые российские сервисы (например, VseGPT). Провайдеры,
   требующие VPN, не подключаются. Адаптер при этом остаётся общим.
2. **GigaChat** требует OAuth2 (client credentials + обновление токена), поэтому
   выносится в отдельный провайдер, а не в общий compatible-адаптер.
3. **LLM — советник.** Модель не меняет статусы, не закрывает инциденты, не
   подтверждает достоверность измерений. Все действия проходят через backend и
   валидацию.
4. **Один активный инцидент на оборудование** для автосоздания. При этом ручное
   API допускает несколько инцидентов на оборудование (осознанно).
5. На текущем этапе в конфиге один `compatible`-endpoint; несколько именованных
   провайдеров — развитие этапа экспериментов.
6. Тесты не обращаются к внешним API: HTTP-транспорт подменяется.

## 6. Инциденты: жизненный цикл

### 6.1. Статусы

`open → in_progress → resolved → closed`

Допустимые переходы:

| Из | В |
| --- | --- |
| `open` | `in_progress`, `closed` |
| `in_progress` | `resolved`, `open`, `closed` |
| `resolved` | `closed`, `in_progress` |
| `closed` | `open` |

Недопустимый переход → `409 Conflict`, состояние не меняется и не пишется событие.
Повторный PATCH с текущим статусом → `200` без нового события.

### 6.2. Аудит

События: `created`, `status_changed` (`from`, `to`, `actor`), `assigned`
(`from`, `to`, `actor`), `deviation_linked` (`deviation_id`).
`actor` пока `system`; передача исполнителя из аутентификации — в открытых вопросах.

### 6.3. Автосоздание из отклонений

- Триггер: новое отклонение, созданное правилом мониторинга.
- Severity по метрике: `temperature_c → critical`, `vibration_mm_s → high`,
  остальные → `medium`.
- Если у оборудования есть активный инцидент (`open`/`in_progress`), отклонение
  привязывается к нему; новый инцидент не создаётся.
- `resolved`/`closed` не блокируют создание нового.
- Телеметрия, отклонения, инцидент, связь и события пишутся одной транзакцией.
- Работает и для HTTP, и для MQTT.

## 7. Телеметрия и мониторинг

1. Измерение поступает по HTTP (`POST /equipment/{id}/telemetry`) или MQTT
   (топик `factorymind/equipment/+/telemetry`).
2. Для MQTT проверяется `event_id`; повторное сообщение игнорируется.
3. Активные правила оборудования сравнивают показатель с порогом (`gt`/`lt`).
4. При срабатывании создаётся `equipment_deviations` и автоинцидент (см. 6.3).
5. Отсутствующие метрики не проверяются; нечисловые и `NaN`/`Inf` отклоняются.

Валидация: `temperature_c` — конечное число, `vibration_mm_s` ≥ 0 и конечное,
давления конечные, ток/частота/расход ≥ 0.

- длительные операции (эксперименты) — вне HTTP-запроса (этап 5).

## 9. AI Gateway

### 9.1. Интерфейс

```python
class LLMProvider(Protocol):
    name: str
    model: str

    def chat(
        self,
        messages: list[ChatMessage],
        *,
        model: str | None = None,
        temperature: float = 0.0,
        max_tokens: int | None = None,
    ) -> LLMResponse: ...
```

Ответ нормализуется в `LLMResponse`: `provider`, фактическая `model`, `content`,
`latency_ms`, `usage.prompt_tokens`, `usage.completion_tokens`.
`usage` может быть `None` — «провайдер не сообщил», а не ноль.

### 9.2. Провайдеры

| Имя | Транспорт | Особенности |
| --- | --- | --- |
| `ollama` | `POST {OLLAMA_BASE_URL}/api/chat` | локально, `stream: false`, `options.temperature`, `options.num_predict` |
| `compatible` | `POST {COMPATIBLE_BASE_URL}/chat/completions` | VseGPT и другие совместимые API; `Bearer`/`Api-Key`; `max_tokens` опционален |

Модель можно переопределить в каждом вызове (`model`), поэтому один endpoint
обслуживает несколько моделей. Фактическая модель из ответа сохраняется: она
может отличаться от запрошенной (версия/тег) и важна для воспроизводимости.

### 9.3. Конфигурация

| Переменная | Обязательность | Смысл |
| --- | --- | --- |
| `OLLAMA_BASE_URL` | нет (default `http://127.0.0.1:11434`) | адрес Ollama |
| `OLLAMA_MODEL` | нет (default `llama3.1`) | модель по умолчанию |
| `COMPATIBLE_BASE_URL` | да для `compatible` | например, `https://api.vsegpt.ru/v1` |
| `COMPATIBLE_MODEL` | нет, если модель передаётся в запросе | модель по умолчанию |
| `COMPATIBLE_API_KEY` | зависит от провайдера | ключ |
| `COMPATIBLE_AUTH_SCHEME` | нет (default `Bearer`) | `Bearer` или `Api-Key` |
| `LLM_TIMEOUT_SECONDS` | нет (default `60`) | таймаут HTTP-вызова |

При отсутствии `COMPATIBLE_BASE_URL` или модели — `ProviderNotConfiguredError`,
а не вызов чужого API.

### 9.4. Ошибки и HTTP-маппинг (этап 3.3)

| Доменная ошибка | Причина | HTTP |
| --- | --- | --- |
| `LLMTimeoutError` | провайдер не ответил за таймаут | `504` |
| `LLMProviderError` | отказ провайдера (4xx/5xx, сеть) | `502` |
| `LLMResponseError` | неJSON, нет `content`, пустой ответ | `502` |
| `ProviderNotConfiguredError` | не задан URL/модель | `500` (ошибка конфигурации) |
| `UnknownProviderError` | неизвестное имя провайдера | `422` |

### 9.5. Журнал вызовов (этап 3.2)

Каждый вызов сохраняется в `llm_calls`:

- провайдер, фактическая модель, версия промпта;
- входные сообщения и параметры генерации (JSON);
- текст ответа либо тип/текст ошибки;
- `latency_ms` (замер на клиенте, `perf_counter`), токены;
- `created_at`.

Ошибочные вызовы тоже сохраняются — иначе нельзя посчитать надёжность модели
(критерий 7).

## 10. Эксперименты и оценка (этап 4)

### 10.1. Сценарий эксперимента

Сценарий — JSON-документ с производственным контекстом: оборудование, показания,
границы, история инцидентов, вопрос и требуемый формат ответа. Сценарий
версионируется вместе с промптом.

Эксперимент фиксирует:

- сценарий;
- набор моделей (провайдер + модель);
- версию промпта;
- параметры генерации (temperature, max_tokens и т.д.);
- набор критериев оценки.

### 10.2. Критерии оценки

| Критерий | Что проверяет | Основной метод |
| --- | --- | --- |
| Корректность | верно ли определена проблема (например, превышение порога) | детерминированная проверка по данным |
| Обоснованность | опирается ли ответ на входные данные, нет ли выдуманных фактов | правила + LLM-judge |
| Полнота | учтены ли существенные обстоятельства (повторяемость и т.п.) | LLM-judge по рубрике |
| Работа с неопределённостью | разделены ли факты и гипотезы, указан ли недостаток данных | LLM-judge по рубрике |
| Практическая применимость | разумна ли последовательность действий | LLM-judge + правила |
| Производительность | latency, токены, стоимость | замеры и расчёт |
| Надёжность | поведение при повторах, неполных данных, ошибках API | серия прогонов |

Оценки не сводятся к одному баллу: отчёт содержит оценки по критериям,
обоснование и цитаты/ссылки на данные.

### 10.3. Требования к оценщику

- Рубрики с явными уровнями (например, 0/1/2) и описанием каждого уровня.
- Эталонный набор примеров для калибровки LLM-judge.
- Проверка согласованности: повторные прогоны, сравнение с эталоном.
- Judge не оценивает то, что можно проверить кодом.
- Результаты оценки сохраняются с версией рубрики.

| `GET` | `/incidents` | Список (`status`, `equipment_id`) |
| `GET` | `/incidents/{id}` | Детали, отклонения, события |
| `PATCH` | `/incidents/{id}` | Статус, severity, исполнитель, описание |
| `POST` | `/incidents/{id}/deviations` | Привязать отклонение (идемпотентно) |
| `GET` | `/incidents/{id}/events` | История событий |

Коды: `201` создание, `204` привязка, `404` отсутствующий объект, `409`
недопустимый переход/конфликт связи, `422` ошибка валидации.

### 11.2. Планируемые AI-эндпоинты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/ai/calls` | Выполнить вызов модели и сохранить журнал |
| `GET` | `/ai/calls/{id}` | Карточка вызова |
| `GET` | `/ai/calls` | Журнал с фильтрами (`provider`, `status`, `limit`, `offset`) |
| `POST` | `/experiments` | Создать эксперимент |
| `GET` | `/experiments/{id}` | Статус и результаты |
| `GET` | `/experiments/{id}/report` | Сравнительный отчёт |

Пример запроса (3.3):

```json
{
  "provider": "compatible",
  "model": "openai/gpt-4o-mini",
  "messages": [
    {"role": "system", "content": "Ты аналитик производственных инцидентов"},
    {"role": "user", "content": "Температура выросла с 5 до 11 °C..."}
  ],
  "temperature": 0.0,
  "max_tokens": 512
}
```

Ответ — сохранённый вызов: `id`, `provider`, `model`, `status`, `response_text`,
`latency_ms`, `prompt_tokens`, `completion_tokens`, `created_at`.

## 13. Тестирование

| Уровень | Что проверяется |
| --- | --- |
| Unit | парсинг ответов провайдеров, маппинг ошибок, сборка провайдера |
| Integration | API на SQLite: инциденты, телеметрия, автосоздание, привязки |
| Contract | запрос/ответ провайдеров через `httpx2.MockTransport` |
| Регрессия | N+1 (счётчик SQL), идемпотентность MQTT и привязки отклонений |
| CI | линтер, формат, тесты с покрытием |

Тесты не требуют PostgreSQL, MQTT-брокера и внешних LLM.

## 15. Открытые вопросы

1. **Аутентификация и роли** — когда и в каком виде (JWT, API-ключи)?
2. **Несколько compatible-провайдеров** — хранить конфигурации в БД или в env?
3. **GigaChat** — нужен ли, и когда делать OAuth-провайдер?
4. **Фоновые задачи** — Celery / RQ / ARQ / собственный воркер?
5. **Судья** — какая модель оценивает ответы и как валидируется согласованность?
6. **Хранение промптов и ответов** — retention, ПДн, объём текста в БД.
7. **Конкурентный доступ к инцидентам** — нужен ли `SELECT FOR UPDATE` или
   оптимистическая блокировка (требует тестов на PostgreSQL).

## 16. Глоссарий
