## 1. Назначение и границы проекта

FactoryMind AI — backend-платформа для мониторинга промышленного оборудования,
управления инцидентами и воспроизводимого сравнения ответов языковых моделей на
производственных сценариях.

В проекте два равноправных контура:

1. **Производственная система:** оборудование, телеметрия, правила мониторинга,
   отклонения, инциденты и история их обработки.
2. **AI-платформа:** единый шлюз к моделям, сохранение вызовов и метаданных,
   эксперименты по сравнению моделей и оценка качества ответов.

Модели помогают объяснять инциденты и предлагать действия, но не принимают
критические решения вместо backend. Валидация измерений, переходы статусов и
изменение состояния доменных объектов контролируются кодом.

### 1.1. Цели

- Принимать телеметрию по HTTP и MQTT и фиксировать отклонения.
- Вести инциденты с конечным автоматом статусов и аудитом.
- Предоставлять единый интерфейс к LLM, не зависящий от поставщика и модели.
- Сохранять данные, необходимые для воспроизводимости экспериментов.
- Сравнивать модели по независимым критериям, не сводя результат к одному
  непрозрачному баллу.
- Разделять объективные проверки кодом и субъективные оценки LLM-as-a-Judge.

### 1.2. Не входит в текущий горизонт

- UI и личный кабинет.
- Автоматическое закрытие инцидентов языковой моделью.
- Полноценное управление производственными заказами и расчёт расписания.
- Аутентификация и разграничение ролей — до отдельного решения.

Эти пункты не следует самовольно добавлять в MVP. Их можно обсуждать как отдельные
этапы развития.

### 1.3. Акторы

- **Оператор или инженер:** просматривает инциденты, назначает исполнителей,
  меняет статусы.
- **Аналитик или исследователь:** создаёт эксперименты, сравнивает модели,
  анализирует отчёты.
- **Оборудование или симулятор:** публикует телеметрию в MQTT.
- **Внешние клиенты:** взаимодействуют с REST API.

## 2. Технологический стек и общие ограничения

Базовый стек спецификации:

- Python 3.12.
- FastAPI.
- Pydantic 2 и pydantic-settings.
- SQLAlchemy 2 и Alembic.
- PostgreSQL 17.
- paho-mqtt для MQTT.
- httpx2 для HTTP-взаимодействий.
- structlog для структурированных логов.
- pytest, Ruff.
- Docker Compose для локальной инфраструктуры.

Проверяй реальные версии в `pyproject.toml` и lock-файле. Этот список не является
разрешением обновлять зависимости без необходимости.

**Ограничения:**

- Внешние провайдеры должны быть доступны без VPN. Основные варианты — локальная
  Ollama и Chat Completions-совместимые сервисы, например VseGPT.
- GigaChat использует OAuth2 (client credentials и обновление токена) и должен быть
  отдельным адаптером, а не искусственно втиснут в общий compatible-адаптер.
- На текущем этапе допускается один настроенный compatible endpoint; несколько
  именованных провайдеров — предмет дальнейшего развития.
- Тесты не должны обращаться к реальным внешним API.
- Сбой LLM-провайдера не должен нарушать работу производственного контура.

## 3. Архитектурные принципы

Используй модульный монолит с разделением ответственности по доменам:

- **Equipment** — оборудование.
- **Telemetry** — приём и хранение измерений, MQTT.
- **Monitoring** — правила и отклонения.
- **Incidents** — жизненный цикл инцидентов, аудит и связи.
- **AI Gateway** — провайдеры LLM и нормализация ответов.
- **Experiment Engine** — сценарии, прогоны и версии промптов.
- **Evaluation Engine** — детерминированные проверки и оценки качества.

Основные правила:

- Доменный слой не должен зависеть от конкретного LLM-вендора.
- Общение с моделями проходит через интерфейс `LLMProvider` и нормализованный
  `LLMResponse`.
- Доменная логика не должна знать об HTTP-кодах; преобразование доменных ошибок
  в HTTP-ответы выполняется на API-слое.
- Бизнес-правила не должны быть размазаны по роутерам, ORM-моделям и MQTT callback.
  Выделяй сервисный слой там, где есть самостоятельная бизнес-операция.
- Транзакционные границы должны соответствовать целостной доменной операции.
- Длительные эксперименты не должны выполняться внутри обычного HTTP-запроса;
  для них предусмотрено фоновое выполнение.
- Не вводи абстракции «на будущее» без конкретного сценария использования.
- Не усложняй MVP микросервисами: текущая архитектурная цель — модульный монолит.

## 4. Производственный контур

### 4.1. Оборудование

Сущность `equipment` содержит:

- `code` — уникальный код;
- `name`;
- `equipment_type`;
- `location`;
- `is_active`.

Операции API: создание, чтение, обновление и получение списка оборудования.
Соблюдай существующий стиль схем, сервисов, репозиториев и роутеров проекта.

### 4.2. Телеметрия

Телеметрия поступает двумя путями:

- **HTTP:** `POST /equipment/{id}/telemetry`;
- **MQTT:** `factorymind/equipment/+/telemetry`.

Таблица `equipment_telemetry` хранит `equipment_id`, `measured_at`,
`temperature_c`, `vibration_mm_s` и дополнительные необязательные метрики.

**Правила валидации:**

- Отсутствующая метрика не проверяется.
- Нечисловые значения, `NaN` и `Inf` отклоняются.
- `temperature_c` — конечное число.
- `vibration_mm_s` — конечное число, не меньше нуля.
- Давление должно быть конечным числом.
- Ток, частота и расход должны быть неотрицательными значениями.
- Не ослабляй валидацию ради удобства приёма некорректных данных.

История телеметрии поддерживает `limit`, `offset`, `since`, `until`.

### 4.3. MQTT и идемпотентность

- Повторная обработка одного MQTT-сообщения предотвращается по `event_id`.
- Таблица `processed_mqtt_events` использует `event_id` как первичный ключ и хранит
  время обработки.
- Идемпотентность должна обеспечиваться на уровне БД/транзакции, а не только
  предварительной проверкой в памяти.
- Тестируй повторную доставку одного события.
- Не считай защиту от повторного `event_id` решением всех проблем конкурентного
  выполнения: отдельно учитывай гонку при автосоздании инцидентов.

### 4.4. Правила мониторинга и отклонения

`monitoring_rules` содержит оборудование, метрику, оператор (`gt`/`lt`), порог
и флаг активности.

При поступлении измерения:

1. Выбрать активные правила соответствующего оборудования.
2. Сравнить только присутствующие и валидные метрики.
3. При срабатывании создать `equipment_deviations`.
4. Запустить доменную логику привязки к активному инциденту или автосоздания нового.

`equipment_deviations` хранит `equipment_id`, `telemetry_id`, `rule_id`,
`metric_name`, `observed_value`, `threshold_value`, `message`, `detected_at`,
`is_resolved`.

### 4.5. Инциденты и конечный автомат

Таблица `incidents` содержит `equipment_id`, `title`, `status`, `severity`,
`assigned_to`, `resolved_at`.

Допустимые статусы и переходы:

| Текущий статус | Допустимые следующие статусы |
| --- | --- |
| `open` | `in_progress`, `closed` |
| `in_progress` | `resolved`, `open`, `closed` |
| `resolved` | `closed`, `in_progress` |
| `closed` | `open` |

**Требования:**

- Недопустимый переход возвращает `409 Conflict`; состояние и аудит не меняются.
- `PATCH` с тем же статусом возвращает успешный ответ без нового события.
- Ручное API может создавать несколько инцидентов на одном оборудовании.
- Для автосоздания допускается один активный инцидент на оборудование.
- Активными считаются `open` и `in_progress`.
- Если активный инцидент существует, новое отклонение связывается с ним.
- `resolved` и `closed` не блокируют создание нового инцидента.

Аудит хранится в `incident_events` (JSON `payload`, дата, тип события).
Поддерживаемые события:

- `created`;
- `status_changed` с `from`, `to`, `actor`;
- `assigned` с `from`, `to`, `actor`;
- `deviation_linked` с `deviation_id`.

Пока `actor` может быть `system`; получение пользователя из аутентификации относится
к будущему этапу.

Связь `incident_deviations` должна обеспечивать уникальность `deviation_id`.
Повторная привязка обрабатывается идемпотентно; привязка отклонения, принадлежащего
другому оборудованию, должна приводить к `409 Conflict`.

**Автосоздание:**

- Триггер — новое отклонение, созданное правилом мониторинга.
- Severity: `temperature_c` → `critical`; `vibration_mm_s` → `high`; прочие метрики
  → `medium`.
- Запись телеметрии, отклонений, инцидента, связей и событий выполняется в одной
  транзакции.
- Поведение одинаково для HTTP- и MQTT-пути.

Автоматический путь сериализуется транзакционной PostgreSQL advisory-lock по
`equipment_id`. Блокировка берётся только после создания отклонения и освобождается
автоматически при `commit`/`rollback`. Частичный уникальный индекс не используется,
поскольку ручное API вправе создавать несколько активных инцидентов; блокировка
`SELECT FOR UPDATE` по таблице инцидентов не защищает случай, когда активной строки
ещё нет.
Конкурентное поведение проверяется отдельным тестом на PostgreSQL, поскольку SQLite
не воспроизводит этот механизм.

## 5. AI Gateway

### 5.1. Контракт провайдера

Общий интерфейс `LLMProvider` предоставляет `chat(...)` и возвращает нормализованный
`LLMResponse`.

Ожидаемые данные ответа:

- `provider`;
- фактическая `model`;
- `content`;
- `latency_ms`;
- `usage.prompt_tokens`;
- `usage.completion_tokens`.

`usage=None` означает, что провайдер не сообщил статистику. Не подменяй это нулём.

Техническая спецификация описывает синхронный контракт `chat`. При развитии API и
экспериментов отдельно оцени необходимость async-контракта: не смешивай синхронные
и асинхронные реализации неявно. Сравни варианты с учётом FastAPI, HTTP-клиента,
нагрузки и фоновых задач, прежде чем менять контракт.

### 5.2. Провайдеры

**Ollama**

- `POST {OLLAMA_BASE_URL}/api/chat`;
- `stream: false`;
- параметры генерации передаются в `options`, включая `temperature` и `num_predict`.

**Chat Completions-compatible**

- `POST {COMPATIBLE_BASE_URL}/chat/completions`;
- поддержка авторизации `Bearer` и `Api-Key`;
- `max_tokens` передаётся, если задан;
- подходит для VseGPT и других совместимых API, но не предполагай полную идентичность
  поведения всех поставщиков.

Модель можно переопределять на уровне вызова. Сохраняй фактическое имя модели,
полученное от провайдера: оно может отличаться от запрошенного и важно для
воспроизводимости.

### 5.3. Конфигурация

| Переменная | Назначение |
| --- | --- |
| `OLLAMA_BASE_URL` | По умолчанию `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | Модель по умолчанию, например `llama3.1` |
| `COMPATIBLE_BASE_URL` | Обязателен для compatible-провайдера |
| `COMPATIBLE_MODEL` | Модель по умолчанию, если не задана в запросе |
| `COMPATIBLE_API_KEY` | Ключ, если требуется провайдером |
| `COMPATIBLE_AUTH_SCHEME` | `Bearer` или `Api-Key`, по умолчанию `Bearer` |
| `LLM_TIMEOUT_SECONDS` | Таймаут HTTP-вызова, по умолчанию 60 секунд |

Если обязательная конфигурация отсутствует, возвращай `ProviderNotConfiguredError`,
не отправляй запрос на случайный или чужой endpoint.

### 5.4. Ошибки

Ожидаемые доменные ошибки и HTTP-маппинг для API-этапа:

| Доменная ошибка | Причина | HTTP |
| --- | --- | --- |
| `LLMTimeoutError` | Таймаут | `504` |
| `LLMProviderError` | Ошибка провайдера или сети | `502` |
| `LLMResponseError` | Некорректный JSON/структура или пустой ответ | `502` |
| `ProviderNotConfiguredError` | Не задана конфигурация | `500` |
| `UnknownProviderError` | Неизвестное имя провайдера | `422` |

Не протаскивай `HTTPException` в доменный код. Не раскрывай пользователю ключи,
заголовки авторизации или чувствительные фрагменты запросов в тексте ошибки.

### 5.5. Журнал вызовов

Таблица `llm_calls` сохраняет:

- провайдера и фактическую модель;
- версию промпта;
- входные сообщения и параметры генерации;
- текст ответа или тип/текст ошибки;
- latency, число prompt/completion tokens;
- время создания.

Ошибочные вызовы тоже сохраняются: без них нельзя достоверно оценивать
надёжность провайдера. Продумай политику хранения и не записывай секреты.

## 6. Эксперименты и оценка качества

### 6.1. Эксперимент

Эксперимент фиксирует:

- JSON-сценарий с производственным контекстом: оборудование, измерения, пороги,
  история инцидентов, вопрос и ожидаемый формат ответа;
- набор моделей (провайдер + модель);
- неизменяемую версию промпта;
- параметры генерации (`temperature`, `max_tokens` и др.);
- набор критериев оценки.

Запуск одного сценария должен позволять сравнить несколько моделей в сопоставимых
условиях. Сохраняй входы и параметры, достаточные для повторения эксперимента.

### 6.2. Данные и критерии оценки

Планируемые сущности:

- `prompt_versions`: имя, версия, содержимое; уникальность `(name, version)`;
- `experiments`: имя, JSON-сценарий, критерии, версия промпта;
- `experiment_runs`: эксперимент, провайдер, модель, параметры, статус, время
  начала/окончания, ошибка;
- `evaluations`: вызов, оценщик, критерии, сводка;
- `evaluation_results`: критерий, оценка, доказательства, комментарий.

Критерии:

1. **Корректность** — детерминированная проверка по входным данным.
2. **Обоснованность** — опора на факты, отсутствие выдуманных данных.
3. **Полнота** — учёт существенных обстоятельств.
4. **Работа с неопределённостью** — разделение фактов и гипотез, указание нехватки
   данных.
5. **Практическая применимость** — разумность предложенных действий.
6. **Производительность** — latency, токены, стоимость.
7. **Надёжность** — поведение при повторах, неполных данных и ошибках API.

Не своди всё к одному общему баллу. Отчёт должен показывать оценки по критериям,
обоснование и ссылки/цитаты на использованные данные.

### 6.3. LLM-as-a-Judge

- То, что можно проверить кодом, проверяется кодом, а не судьёй.
- Используй рубрики с явными уровнями, например 0/1/2, и описанием каждого уровня.
- Храни версию рубрики вместе с результатом.
- Подготовь эталонные примеры и проверяй согласованность оценщика с эталоном.
- Учитывай вариативность судьи и необходимость повторных прогонов.
- Не выдавай субъективную оценку модели за объективный факт.

### 6.4. Частичные результаты и сбои

При сравнении нескольких моделей отказ одного провайдера не должен уничтожать
успешные результаты остальных. Предусмотри отдельный статус каждого прогона,
сохранение частичных результатов и понятное описание ошибки. Повторные попытки,
backoff, восстановление после перезапуска и защита от повторного запуска относятся
к этапу фоновой надёжности.

## 7. API

### 7.1. Производственные endpoints

Заявленные в спецификации endpoints:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | Проверка живости |
| `POST` | `/equipment` | Создание оборудования |
| `GET` | `/equipment` | Список оборудования |
| `GET` | `/equipment/{id}` | Карточка оборудования |
| `PATCH` | `/equipment/{id}` | Обновление оборудования |
| `POST` | `/equipment/{id}/telemetry` | Приём показаний |
| `GET` | `/equipment/{id}/telemetry` | История измерений |
| `POST` | `/equipment/{id}/monitoring-rules` | Создание правила |
| `GET` | `/equipment/{id}/monitoring-rules` | Правила оборудования |
| `GET` | `/equipment/{id}/deviations` | Отклонения |
| `POST` | `/incidents` | Создание инцидента |
| `GET` | `/incidents` | Список с фильтрами |
| `GET` | `/incidents/{id}` | Детали, отклонения, события |
| `PATCH` | `/incidents/{id}` | Обновление инцидента |
| `POST` | `/incidents/{id}/deviations` | Привязка отклонения |
| `GET` | `/incidents/{id}/events` | История событий |

Заявленные коды: `201` при создании, `204` при привязке, `404` при отсутствии
объекта, `409` при конфликте состояния/связи, `422` при ошибке валидации.
Фактический контракт всегда проверяй по текущему коду и OpenAPI.

### 7.2. AI endpoints

Реализовано:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/ai/calls` | Вызов модели и сохранение журнала; `201` с карточкой |
| `GET` | `/ai/calls` | Журнал с фильтрами `provider`, `status` и пагинацией |
| `GET` | `/ai/calls/{id}` | Карточка вызова |

Ошибки вызова: `504` при таймауте, `502` при отказе провайдера или некорректном
ответе, `422` для неизвестного провайдера, `500` при отсутствии конфигурации.
Ошибочный вызов сохраняется, в `detail` возвращается `call_id`.

Планируется (этап 4):

- `POST /experiments` — создание эксперимента.
- `GET /experiments/{id}` — статус и результаты.
- `GET /experiments/{id}/report` — сравнительный отчёт.

Не считай планируемые endpoints реализованными: сначала проверь текущий код и тесты.

## 8. Нефункциональные требования

- Качество: `ruff check`, `ruff format --check`, `pytest`.
- Целевое покрытие тестами — не менее 85%; проверяй реальную конфигурацию покрытия.
- CI: GitHub Actions на push в `main` и pull request; установка зависимостей
  с lock-файлом (`uv sync --locked`, если это соответствует текущему проекту).
- Интеграционные тесты API — на SQLite in-memory, если функциональность совместима
  с SQLite.
- Тесты не требуют внешнего LLM API или MQTT-брокера; транспорт подменяется.
- Секреты задаются переменными окружения и не логируются.
- Логи — структурированные (structlog, JSON в соответствующем окружении).
- `request_id` должен проходить через контекст запроса и логи.
- Для воспроизводимости сохраняются фактическая модель, версия промпта, параметры,
  входные данные, время и доступная статистика токенов.
- API без LLM должен оставаться быстрым; LLM-вызовы ограничиваются таймаутом.
- Prometheus/Grafana относятся к отдельному этапу.

## 9. Тестирование

Ожидаемые уровни:

- **Unit:** парсинг ответов провайдеров, маппинг ошибок, сборка провайдеров,
  доменные переходы и бизнес-правила.
- **Integration:** API на SQLite, телеметрия, автосоздание инцидентов, связи и аудит.
- **Contract:** запросы и ответы провайдеров через `httpx2.MockTransport`.
- **Regression:** идемпотентность MQTT и привязок, отсутствие N+1 там, где это важно
  (при необходимости — счётчик SQL-запросов).
- **CI:** линтер, форматирование, тесты и проверка покрытия.

Обязательно проверяй граничные случаи:

- повторное MQTT-событие;
- отсутствующая метрика и некорректное числовое значение;
- правило `gt` и `lt`;
- переходы статусов, включая недопустимые и повторные;
- повторная привязка отклонения;
- привязка чужого отклонения;
- наличие активного и завершённого инцидента при автосоздании;
- сбой, таймаут, некорректный ответ и отсутствие конфигурации LLM-провайдера;
- частичный отказ набора моделей в эксперименте;
- конкурентное автосоздание инцидента — отдельные проверки на PostgreSQL.

## 11. Будущее развитие — за пределами текущего MVP

Следующие идеи сохраняют первоначальное направление проекта, но не входят
автоматически в текущий объём работ.

### 11.1. Симулятор датчиков

Так как физического промышленного оборудования для разработки нет, симулятор —
важная часть демонстрации проекта. Планируемые возможности:

- несколько виртуальных датчиков на оборудовании;
- нормальные, аномальные и аварийные сценарии показаний;
- изменение частоты и характера измерений;
- пропуски, задержки, повторная отправка сообщений и восстановление соединения;
- управление сценарием симуляции;
- публикация событий через MQTT, с возможностью тестировать HTTP-путь отдельно.

Не смешивай генератор тестовых данных с доменной логикой мониторинга. Симулятор
должен производить входные события так, как если бы они поступали от внешнего
оборудования.

### 11.2. Явная модель Sensor

В текущей описанной модели телеметрия связана с оборудованием, но отдельная таблица
датчиков не определена. Перед реализацией уточнить, требуется ли сущность `sensors`
для поддержки нескольких датчиков на одном оборудовании, их типов, поддерживаемых
метрик, активности и контроля отсутствия данных. Не добавляй таблицу без согласования
модели и сценариев.

### 11.3. Производственный процесс

В дальнейшем возможно расширение домена на процесс «от входящего заказа до готового
продукта», включая производственные операции и контроль качества. Управление заказами
и расписанием не входит в текущий MVP; для расписания предпочтителен детерминированный
планировщик, а не решение LLM.

### 11.4. CRM-интеграции

Предусмотреть возможность адаптеров для Bitrix24 и amoCRM. Интеграции должны быть
изолированы за интерфейсами/адаптерами, чтобы доменная логика не зависела от
конкретной CRM. Реализацию отложить до появления согласованного сценария и контракта.

## 12. Открытые архитектурные вопросы

Не закрывай эти вопросы предположениями, если решение влияет на архитектуру:

1. Аутентификация и роли: JWT, API-ключи, сроки и границы внедрения.
2. Несколько compatible-провайдеров: конфигурация через env или хранение в БД.
3. Нужен ли отдельный GigaChat OAuth2-провайдер и когда.
4. Фоновые задачи: Celery, RQ, ARQ или собственный worker.
5. Выбор модели-судьи и способ калибровки согласованности.
6. Retention, приватность и допустимый объём хранения промптов/ответов.
7. Синхронный или асинхронный контракт LLM-провайдеров.
8. Как сохранять частичные результаты эксперимента и восстанавливаться после сбоев.
9. Нужна ли полноценная сущность Sensor и как она связана с Equipment и Telemetry.

Для каждого существенного решения фиксируй краткое обоснование, альтернативы и
последствия. Если проекту понадобится журнал решений, предложи ADR-файлы в отдельной
папке, не создавая их без необходимости.

## 13. Правила внесения изменений

При реализации новой функции:

1. Определи доменный сценарий и ожидаемое поведение.
2. Проверь, где должна находиться ответственность: API, сервис, домен,
   инфраструктура.
3. Определи контракты входных и выходных данных.
4. Продумай ошибки и граничные случаи до написания основной логики.
5. Добавь/обнови тесты вместе с реализацией.
6. Проверь миграции и обратную совместимость.
7. Обнови документацию, если изменились API, настройки или поведение.

При исправлении бага:

1. Сначала воспроизведи проблему тестом или минимальным сценарием.
2. Найди первопричину, а не маскируй симптом.
3. Внеси минимальное согласованное исправление.
4. Добавь регрессионный тест.
5. Проверь связанные сценарии.

При рефакторинге:

- Сохраняй внешнее поведение, если изменение контракта не является целью.
- Не объединяй несвязанные изменения в один diff.
- Не добавляй новые зависимости без обоснования.
- Не заменяй понятный код абстракцией ради абстракции.

## 14. Definition of Done

Задача считается завершённой, когда:

- реализовано согласованное поведение;
- добавлены или обновлены релевантные тесты;
- тесты и проверки выполнены либо явно указано, почему они не запускались;
- миграции согласованы с моделями и историей схемы;
- ошибки и граничные случаи обработаны;
- секреты и чувствительные данные не раскрываются;
- документация обновлена, если изменился контракт;
- diff не содержит посторонних изменений;
- разработчику понятно, что сделано и почему.

## 15. Глоссарий

| Термин | Значение |
| --- | --- |
| Отклонение | Зафиксированное превышение или недобор показателя по правилу |
| Инцидент | Рабочий процесс устранения отклонения со статусами и аудитом |
| Активный инцидент | Инцидент со статусом `open` или `in_progress` |
| Провайдер | Адаптер к API модели (Ollama, compatible и др.) |
| Эксперимент | Сравнительный прогон сценария на наборе моделей |
| Прогон | Вызов одной модели в рамках эксперимента |
| Judge | Оценщик качества ответа, в том числе LLM |
| Воспроизводимость | Возможность повторить прогон с теми же входами и параметрами |
